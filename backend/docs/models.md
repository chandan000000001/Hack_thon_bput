# CYBERGUARD Models & Algorithms Details

CYBERGUARD's detection layer is **hybrid**: transparent heuristic engines (every indicator enumerable, every score reproducible) combined with **four trained models** served from `ml/models/` via `app/services/ml_inference.py`. The LLM providers (Groq first, then OpenRouter, via `app/ai/llm_gateway.py`) are used **only** to write human-readable explanations — they never produce scores. Offline metrics live in [`evidence/reports/evaluation.md`](../../../evidence/reports/evaluation.md) (generated by `scripts/evaluate.py`; generated 2026-09-07).

## Scoring engine (shared by all modules)

`app/services/scoring_service.py`

- Each heuristic indicator carries a severity: **critical = 25**, **high = 15**, **medium = 5** points.
- `calculate_score(indicators)` sums weights, capped at 100.
- `get_severity(score)` maps to bands: **safe 0–20, low 21–40, medium 41–60, high 61–80, critical 81–100**.
- Heuristic modules are **flagged** at `risk_score >= 41` in the evaluation harness; media forensics is flagged at `manipulation_probability >= 0.5`.

## Hybrid blending rule (all ML-backed detectors)

```
hybrid_score = max(heuristic_score, round(0.45 * heuristic_score + 0.55 * ml_probability * 100))
```

- **Monotonic / safety principle:** a trained model may raise a score but may **never lower it below the heuristic verdict** — a strong heuristic signal (e.g. a C2-port exfiltration event) cannot be diluted by a weak or mismatched ML signal.
- The ML contribution is appended as a `type: "ml_model"` indicator carrying the numeric probability; `split_ml_indicator()` separates it out so it never adds heuristic weight.
- When `ML_ENABLED=false` or a model file is missing, predictors return `None`, no `ml_model` indicator is appended, and behaviour is byte-identical to the heuristics-only pipeline.

## Heuristic engine cards

### 1. Phishing — `app/services/phishing_detector.py`

- **Input:** sender, subject, body. **Output:** indicators + heuristic score.
- **Key heuristics:** leet-tolerant lookalike sender domains (paypa1, micr0soft → per-brand regex with an official-domain allowlist); urgency keywords; credential-request phrases; body URLs (IP hosts, plain HTTP, suspicious TLDs); threat language; SMS layer: 5–6 digit shortcodes, international/long phone numbers, spam vocabulary (txt, claim, winner, loan, cash, free, prize…), digit-to-letter ratio, 4+ consecutive ALL-CAPS words.
- **Weights:** lookalike domain / credential request / malicious URL = critical (25); urgency / threat language / SMS keyword / shortcode / phone = high (15); digit ratio / ALL-CAPS = medium (5).
- **Limitations:** vocabulary-based; novel lures without listed markers score lower; fixed brand allowlist.

### 2. Malicious URL — `app/services/url_detector.py`

- **Input:** single URL string.
- **Key heuristics:** IP-based host; URL length > 75 with Shannon entropy > 4.0; suspicious TLDs (.xyz/.top/.zip/…); brand name in subdomain; plain HTTP; credential path keywords; URLhaus tuning: executable/payload extensions (.exe/.php/.js/.vbs/.hta/…), random high-entropy path segments, excessive digit ratio, abused-TLD + long-path pattern.
- **Weights:** IP host / brand-in-subdomain = critical (25); executable extension, suspicious TLD, HTTP, URLhaus pattern = high (15); length, entropy, random segment, digit ratio, path keywords = medium (5).
- **Limitations:** point-in-time lexical rules; compromised *legitimate* domains with clean paths can pass; no DNS reputation or live page fetching.

### 3. Impersonation — `app/services/impersonation_detector.py`

- **Input:** message text + claimed identity.
- **Key heuristics:** authority keywords in the claimed identity (CEO, CFO, director, principal, bank, IRS, IT support — acronyms matched on word boundaries); pressure phrases (urgent, immediately, do not question, confidential, ASAP); unusual financial requests (gift card, wire transfer, bitcoin, bypass procedure, share codes); secrecy phrases (don't tell anyone, keep this between us).
- **Weights:** authority identity / pressure / secrecy = high (15); unusual request = critical (25).
- **Limitations:** English-only phrase lists; a skilled impersonator avoiding listed phrases scores lower; no sender-history profiling.

### 4. Account takeover — `app/services/account_takeover_detector.py`

- **Input:** list of auth events (`user`, `ip`, `location`, `device`, `status`, `timestamp` — ISO-8601 timestamps).
- **Key heuristics:** failed-login burst (≥ 3 failures per user); impossible travel (successful logins from different locations < 60 min apart); new/unknown device (first device per user in the batch is the baseline); suspicious device agents; success immediately after ≥ 2 consecutive failures.
- **Weights:** impossible travel = critical (25); burst / success-after-failures = high (15); new or unknown device = medium (5).
- **Limitations:** batch-local baselines (no long-term user history); ISO-8601 timestamps only; literal location-string comparison.

### 5. Network / API abuse — `app/services/network_threat_detector.py`

- **Input:** flows (`source_ip`, `dest_ip`, `port`, `bytes_out`, `protocol`) and/or API logs (`endpoint`, `method`, `source_ip`, `status_code`). Module `network` when flows are present, else `api_abuse`.
- **Key heuristics:** outbound volume > 10 MB per flow; C2/backdoor ports (4444, 8888, 1337, 31337, 6667); > 50 requests from one source IP; > 5 HTTP 401s from one source IP.
- **Weights:** C2 port = critical (25); exfiltration, rate abuse, repeated auth failures = high (15).
- **Limitations:** fixed thresholds; no temporal baselining or per-tenant traffic profiles; beaconing detected only implicitly via repeated identical flows.

### 6. Deepfake / media forensics — `app/services/deepfake_detector.py` + `app/services/media_forensics/`

- **Input:** media bytes (image, video, audio ≤ 25 MB).
- **Images:** Error Level Analysis (ELA) via Pillow — JPEG q90 re-encode, per-pixel residual mean/max and 8×8 block variance (splicing), uniform-error maps, missing EXIF, container mismatch.
- **Videos:** ≤ 10 sampled frames (OpenCV) + per-frame ELA + temporal ELA variance + container sanity (fps, frame count).
- **WAV audio:** real signal statistics (clipping ratio, zero-crossing-rate variance, spectral flatness proxy / spectral holes via numpy FFT).
- **Non-WAV audio: SIMULATED** — deterministic SHA-256-derived score returned with `simulated: true` and a **reserved Hugging Face model hook** in `media_forensics/base.py` so a real audio anti-spoofing model can drop in without any API change.
- **Scoring:** `risk_score = max(round(manipulation_probability × 100), indicator_score)`; flagged at `manipulation_probability >= 0.5`; the response always carries `method` and `simulated` flags.
- **Limitations:** ELA is a manipulation-forensics heuristic, not a deepface/lip-sync model — calibrated on synthetic gradient images and weak against whole-image regeneration; video sampling covers ≤ 10 frames; non-WAV audio results are explicitly simulated; no face/identity or lip-sync analysis.

All media analyzers implement one abstract interface (`app/services/media_forensics/base.py`): `analyze(file_bytes, file_name) -> {authenticity_score, manipulation_probability, indicators, method, simulated}` — `ImageAnalyzer`, `VideoAnalyzer` and `AudioAnalyzer` are interchangeable in `deepfake_detector.analyze_media`.

## Trained model cards

Artifacts live in `backend/ml/models/`; SHA-256 hashes are recorded in [`evidence/reports/evaluation.md`](../../../evidence/reports/evaluation.md). Training metrics below come from the training pipeline (`ml/train_models.py`, held-out splits produced by `ml/preprocess.py`); detection-level metrics come from `scripts/evaluate.py`.

### 1. Email phishing — `email_phishing_xgb.pkl` + `email_tfidf.pkl`

- **Algorithm:** TF-IDF (max_features 50,000, English stop words) → XGBoost classifier.
- **Dataset:** Hugging Face `cybersectony/PhishingEmailDetectionv2.0` (232,809 raw emails → 120,000 sampled; the spec'd primary `pirocheto/phishing-email` is gated on the Hub and was skipped). 80/20 split → **95,996 train / 24,000 held-out test** (verified on disk). Labels: 0 benign, 1 phishing/fraud; ~94% phishing, balanced with `scale_pos_weight = count(benign)/count(phishing)` ≈ 0.06.
- **Training metrics:** accuracy 0.9813, precision 0.9995, recall 0.9807, F1 0.9900.
- **Detection metrics (evaluation report, hybrid, n=24000):** accuracy 0.9705, precision 0.9929, recall 0.9756, **F1 0.9842** (heuristics-only F1: 0.0268). Mean 2.278 ms / P95 8.07 ms.
- **Blending:** 0.45 heuristic / 0.55 ML (`predict_email` on sender + subject + body).
- **Limitations:** one public email distribution — marketing-style ham and non-English phishing under-represented.

### 2. URL malicious — `url_xgb.pkl`

- **Algorithm:** XGBoost over 8 handcrafted features (`extract_url_features` — MUST stay identical to training: length, Shannon entropy, digit ratio, has_ip, has_at_symbol, suspicious TLD, http-only, subdomain count).
- **Dataset:** 500 URLhaus malicious + 500 Umbrella benign, 80/20 split → **800 train / 200 held-out test**.
- **Training metrics:** accuracy 1.0000, precision 1.0000, recall 1.0000, F1 1.0000.
- **Detection metrics (evaluation report, hybrid, n=200):** accuracy 1.0, precision 1.0, recall 1.0, **F1 1.0** (heuristics-only F1: 0.9189). Mean 0.972 ms / P95 3.735 ms.
- **Blending:** 0.45 heuristic / 0.55 ML (`predict_url`).
- **Limitations:** ⚠️ **small-sample caveat** — a perfect F1 on 200 held-out rows reflects a narrow, easily separable feature set and does not predict real-world performance; expect degradation on novel phishing infrastructure.

### 3. Deepfake image CNN — `deepfake_cnn.pt`

- **Algorithm:** PyTorch CNN (Conv 3→16→32 + MaxPool, FC 8192→64→2), 136,354 parameters, 2 epochs (Adam, CrossEntropyLoss, batch 256) on 32×32 images; inference resizes any input to 32×32, Normalize(0.5), `predict_image` returns P(fake) (class index 0 = 'fake').
- **Dataset:** CIFAKE (via the accessible mirror `dragonintelligence/CIFAKE-image-dataset`; 100,000 images on disk: 80,000 train / 20,000 held-out test). Labels: real (CIFAR-10 photos) vs fake (AI-generated).
- **Training metrics:** accuracy 0.9156, precision 0.9122, recall 0.9197, F1 0.9159.
- **Detection metrics (evaluation report, hybrid, deterministic sample of 1000 held-out images):** accuracy 0.5, precision 0.5, recall 1.0, **F1 0.6667** — identical to the heuristics-only row (see limitations).
- **Blending:** for images `manipulation_probability = 0.5 × ELA + 0.5 × CNN`; for videos the CNN is averaged over sampled frames and blended with the ELA temporal score. `simulated` stays `false`.
- **Limitations:** ⚠️ **CIFAKE images are 32×32** — resolution is far below real-world media, so metrics do not transfer to high-resolution photos; the evaluation report flags every sample in its 1000-image deterministic pass (FPR 1.0), reported honestly.

### 4. Network anomaly — `network_xgb.pkl` + `network_scaler.pkl`

- **Algorithm:** scaler + XGBoost over the 4 KDD99 "SF" features (log-duration, label-encoded service, log-src_bytes, log-dst_bytes); the service LabelEncoder is re-derived at load time from `ml/data/raw_network.csv` (deterministic refit).
- **Dataset:** `sklearn.datasets.fetch_kddcup99(subset="SF")` — **73,237 flows** on disk; binary target (normal vs any attack); 80/20 split → **58,589 train / 14,648 held-out test**.
- **Training metrics:** accuracy 0.9995, precision 0.9952, recall 0.9936, F1 0.9944.
- **Detection metrics (evaluation report, hybrid, n=60):** accuracy 0.8333, precision 0.9167, recall 0.7333, **F1 0.8148** (heuristics-only F1: 0.8462). Mean 11.641 ms / P95 33.949 ms.
- **Blending:** 0.45 heuristic / 0.55 ML; each flow dict is mapped to the training features with documented constants (duration and response bytes are absent from the flow schema and use the log-floor constant ln(0.1); service is derived from the destination port, unknown ports → KDD's `other`).
- **Limitations:** ⚠️ **KDD99 is 1998 DARPA evaluation data** — decades-old traffic patterns that barely overlap modern flows; the documented-constant feature mapping is a lossy domain bridge. The hybrid blend here cost 2 false positives (FPR 0.0667) while detection latency rose ~600× vs heuristics-only.

**Account takeover has no trained model** — its hybrid row equals the heuristics-only row (n=60: accuracy 0.8667, precision 1.0, recall 0.7333, F1 0.8462). **Impersonation/message** has no trained model either; the message module's hybrid row (n=600: F1 0.6826 vs heuristics-only 0.6270) reflects the SMS-proxy evaluation described in [`docs/datasets.md`](datasets.md).

### Evaluation headline (from `evidence/reports/evaluation.md`)

Macro averages across the six modules — heuristics-only: accuracy 0.6583, precision 0.8617, recall 0.6311, F1 0.6553; **hybrid: accuracy 0.8212, precision 0.8985, recall 0.8276, F1 0.8324**. Latency covers only local detector + ML inference in a single process (no network, storage or LLM time).

## Explainable AI: provider chain

`app/ai/llm_gateway.py` tries providers strictly in order and returns as soon as one succeeds:

| # | Provider | Timeout | Notes |
|---|----------|---------|-------|
| 1 | Groq | `GROQ_TIMEOUT_SECONDS` (default 20 s) | OpenAI-compatible `api.groq.com` endpoint, model `GROQ_MODEL` (default `llama-3.1-8b-instant`); skipped instantly when `GROQ_API_KEY` is empty |
| 2 | OpenRouter | `OPENROUTER_TIMEOUT_SECONDS` (default 60 s) | strict-JSON instruction, model `OPENROUTER_MODEL` (default `meta-llama/llama-3.1-8b-instruct:free`), app-identifying headers (`HTTP-Referer`, `X-Title: CYBERGUARD`) |
| 3 | rule_based | instant (< 5 ms) | template generated locally from the indicator context when both remote providers fail; never fails |

- **Circuit breakers:** each remote provider sits behind its own `AsyncCircuitBreaker` (`app/ai/async_circuit_breaker.py`; threshold 3 consecutive failures, 60 s recovery window, CLOSED/OPEN/HALF_OPEN states). While a breaker is OPEN the gateway logs `Circuit breaker OPEN for <provider>, skipping to fallback` and moves to the next provider **instantly**.
- **Provenance:** every analysis response carries `explanation_provider` (`openrouter` | `groq` | `rule_based` | `cache:<original_provider>`) and `explanation_latency_ms`. Each provider failure logs one warning line: `LLM provider <name> failed after <ms> ms: <reason>`.
- **Strict JSON contract:** per-module system prompts (`app/ai/prompt_templates.py`) constrain the model to `{"explanation": <paragraph starting with the risk level>, "mitre_techniques": [{"id", "name"}], "recommended_actions": [<action strings>]}`; LLM actions are matched against the seeded 10-entry `response_catalog` and type-cast before insert. The SOC assistant uses `json_mode=false` and grounds answers in the last 20 alerts, citing alert IDs.
- **Cache:** successful explanations are cached in-memory for 3600 s (max 256 entries, thread-safe LRU) keyed by sha256 of module name + normalized input (media: sha256 of the file bytes). Hits return `explanation_provider = "cache:<original_provider>"` with zero latency.
- **Worst-case latency bound:** 20 s (Groq) + 60 s (OpenRouter) + < 1 s (rule_based) per analysis while providers are healthy; typically far less, zero on cache hits, and near-zero once a breaker has tripped. Detection heuristics, ML models, scoring bands and route signatures are unaffected — only the explanation source changes.
